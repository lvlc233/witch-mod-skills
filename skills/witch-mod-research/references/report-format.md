# Research Report Format

用于把第一事实调研结果交给 API、case-guide、builder 或用户。报告必须让后续 agent 看得出结论是怎么来的，而不是只看到“查过了”。

```text
结论等级: 已确认/部分确认/不可确认

问题:

用户线索:
- 用户给出的文件、猜测、现象、问题表条目或已有结论

API 边界:
- API 已确认:
- API 缺失:
- API 警告/禁止:

假设:
- H1:
  - 需要证据:
  - 当前状态: 支持/部分支持/被限制/不可确认
- H2:
  - 需要证据:
  - 当前状态:

调研路径:
- path:line 或文件名，说明为什么查这里

证据矩阵:
| 证据 | 事实等级 | 支持 | 反驳/限制 | 不能证明 |
|---|---|---|---|---|
| path:line | 第一事实/1.5/外部参考 | 支持哪个假设 | 限制或冲突 | 缺少什么 |

冲突与处理:
- API vs 第一事实:
- 模板 vs Example:
- Lib/TypeHint vs API:
- 反编译 vs 文档:
- 外部 Mod vs 官方材料:

最小可确认结论:
- 已确认:
- 可推测但未确认:
- 不可确认/不能推出:

可迁移边界:
- 官方模板规则:
- Example 现象:
- Lib 原版模式:
- 反编译机制:
- 外部 Mod 习惯:

下游建议:
- 给 witch-mod-api:
- 给 witch-mod-case-guide:
- 给 witch-mod-builder:
- 给用户:
```

## 判定准则

- 多个官方模板一致出现，通常比单个 Example 更可推广。
- Example 只证明“官方示例这样写过”，不自动证明“所有 Mod 都应该这样写”。
- Lib/TypeHint 可以帮助识别对象和字段，但仍要区分类型提示、配置样例和运行机制。
- 反编译能解释机制，但必须标注版本、路径和推断链。
- API 没写、模板没出现、Example 没使用都属于负证据；负证据不能证明不存在，但会降低结论等级。
- 只有边界清楚、可复述为干净规则的结论才建议进入 `witch-mod-api`。
