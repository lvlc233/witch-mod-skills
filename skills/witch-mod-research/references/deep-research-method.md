# Deep Research Method

用于复杂问题，例如加载顺序、事件时机、`PackBelong` 机制、字段语义、样例 helper、UI 流程、宠物/使魔这类 API 未完整覆盖的系统设计。

Research 的目标不是“多找几个文件”，而是把用户线索、API 缺口和第一事实整理成可审计的最小结论。结论必须能回答：当前证据支持什么、不支持什么、冲突在哪里、下游 skill 能拿它做什么。

## 输入建模

调研开始前先写清四类输入：

```text
原问题:
用户线索:
- 用户指出的文件、现象、猜测、问题表条目、已有结论
API 边界:
- API 已确认:
- API 缺失:
- API 警告或禁止:
资源范围:
- official/README.zh-CN.md、ModTemplate、DllTemplate、Example、Lib
- 反编译文件或用户提供的其他 Mod
```

用户线索必须进入假设或调研路径。不要把它当作旁白，也不要直接当结论。

## 假设优先

先提出多个互相竞争或互相补充的假设，再查证。每个假设都要写出需要什么证据才能确认或否定。

```text
问题: 怎么做“宠物/使魔系统”？
假设 A: 官方存在独立 Partner 系统，可直接通过 Data 表注册。
需要证据: 模板/Lib 中有 Partner 类配置、TypeHint 有对应类型、Example 使用过。

假设 B: “宠物”只是 Blessing/Relic/Card 效果包装，没有独立系统。
需要证据: 示例通过现有效果实现跟随或触发，没有 Partner 配置。

假设 C: Partner 负责实体/显示，PartnerCard 或其他卡牌负责行为调度。
需要证据: Lib 中 Partner 与 Card/Action/Event 字段有关联，反编译有读取链。

假设 D: 行为加载和动作时机只能从反编译或运行观察确认。
需要证据: 模板/Example/Lib 只能证明字段存在，不能证明调度机制。
```

如果只提出一个假设，容易把第一个搜到的文件误当成答案。复杂机制至少保留一个“不可确认/需要运行验证”的备选假设。

## 调研顺序

1. 查 `../witch-mod-api` 相关 references，明确第二事实的支持度、缺口和禁止越界点。
2. 查 `resources/official/README.zh-CN.md` 和模板 README，找官方明示规则。
3. 查 `ModTemplate/Data` 和 `Text`，确认 CSV 表头、第二行备注、局部 ID、字段和目录约束。
4. 查 `Example`，看官方示例如何落地；只把它标为“样例现象”。
5. 查 `ModTemplate/Scripts/Lib`，尤其是 TypeHint、DataConfigs、原版 Lua 辅助函数，找原版模式和暴露对象。
6. 仍缺机制时，查反编译；标注文件名、版本或压缩包名，并写明推断链。
7. 用户提供其他 Mod 时，只作为外部参考对比，不能覆盖官方事实。

搜索时不要只搜一个关键词。对同一概念至少尝试：字段名、局部 ID、全 ID、中文名、英文类名、相关表名、API 中的对象名。

## 证据权重

按证据类型给结论定边界：

| 证据类型 | 能支持 | 不能直接支持 |
|---|---|---|
| 官方明示规则 | 文档规则、模板约束、命名要求 | 未写出的运行机制 |
| 官方模板字段 | 可填写字段、CSV 结构、目录结构 | 字段生效时机 |
| 官方 Example | 官方示例这样写过 | 全局最佳实践或唯一写法 |
| Lib 原版模式 | 原版配置惯例、字段组合、对象形态 | Mod API 保证或稳定兼容 |
| TypeHint/API 暴露 | 可调用对象、方法、字段名 | 方法内部逻辑 |
| 反编译机制 | 读取链、调度链、实际分支 | 未来版本稳定性 |
| 外部 Mod | 社区习惯、可参考实现 | 官方规则 |

同一结论最好有两类以上证据支撑。只有单一证据时必须缩小表达，例如“Example 中可见”而不是“应该这样写”。

## 证据矩阵

把证据写成矩阵，不要写成散文堆砌：

```text
| 证据 | 事实等级 | 支持 | 反驳/限制 | 不能证明 |
| path:line | 第一事实/1.5/外部参考 | 支持哪个假设 | 与哪些文件冲突或只适用于哪里 | 还缺什么机制 |
```

证据矩阵要包含负证据：例如 API 没写、模板没有字段、Example 没使用、Lib 只有原版数据无 Mod 示例。负证据不能证明不存在，但能限制结论强度。

## 冲突处理

遇到冲突时按以下方式写，不要自动调和：

- API 与第一事实冲突：标出 API 是第二事实，第一事实路径是什么；建议 API 修订或保持待确认。
- 模板与 Example 冲突：模板优先说明“可填写结构”，Example 只说明“某个官方示例写法”。
- Lib 字段存在但 API 未记录：只能说“原版配置存在该模式”，不能说“Mod 稳定支持”。
- TypeHint 有字段但没有示例：只能说“对象形态暴露”，不能说“推荐用法已确认”。
- 反编译与文档冲突：写明版本和读取链；除非有运行验证，否则不要覆盖所有版本。
- 外部 Mod 与官方材料冲突：外部 Mod 只能作为候选方案或兼容风险。

## 最小可确认结论

结论必须拆成三层：

```text
已确认:
- 当前证据直接支持的事实。

可推测但未确认:
- 证据倾向支持，但缺少源码链、运行观察或官方明示。

不可确认/不能推出:
- 当前证据不能回答的问题，以及为什么不能回答。
```

如果用户问“怎么写”，research 只能输出可实现 brief 和风险，不直接生成文件。交给 `witch-mod-builder` 前必须保留未确认点。

## 可迁移边界

每个结论都要说明能迁移到哪里：

- 官方模板规则：可作为新 Mod 的结构约束。
- 单个 Example 现象：只能作为案例参考，不能推广为全局规则。
- Lib 原版模式：可作为原版配置参考，迁移到 Mod 时需要 API/运行验证。
- 反编译机制：可解释当前版本机制，但要标注版本风险。
- 外部 Mod 习惯：只能作为实现灵感和兼容性线索。

## 下游输出

Research 报告要给四类下游明确接口：

```text
给 witch-mod-api:
- 可沉淀的干净规则:
- 不应沉淀的原因:

给 witch-mod-case-guide:
- 可复用案例模式:
- 案例需要继续调研的点:

给 witch-mod-builder:
- 可执行 brief:
- 应复制的官方模板:
- 必须保留的风险和验证清单:

给用户:
- 当前最小结论:
- 仍需用户提供或运行验证的问题:
```

只有达到“官方明示规则”或“模板/Example/Lib/源码多方一致且边界清楚”的结论，才建议进入 `witch-mod-api`。案例性、组合性、带风险的内容优先进入 `witch-mod-case-guide` 或 builder brief。
